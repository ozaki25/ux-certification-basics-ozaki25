# lesson30: 継続的なUX改善（DevOps・DesignOps） — リリース後も改善し続ける仕組み

## このレッスンで学ぶこと

- 「リリースして終わり」ではなく、運用しながらUXを改善し続ける考え方を理解する
- DevOps（開発と運用の壁をなくす文化・プラクティス）の目的と代表的な手法を知る
- DesignOps（デザイン業務の仕組み化）の目的と整備する領域を知る
- 継続的なUX改善と高速改善（[lesson04](/lessons/lesson04/)）・行動データ分析（[lesson21](/lessons/lesson21/)）の関係を説明できる

## 継続的なUX改善の必要性

UXデザインは、サービスをリリースした時点では完成しません。理由は大きく3つあります。

- ユーザーの使い方や期待は、実際に使われ始めてから初めて見えてくる
- 競合・技術・社会の環境が変わり続けるため、今日の最適が明日も最適とは限らない
- 行動データが蓄積されるほど、改善の打ち手の精度が上がる

[lesson04](/lessons/lesson04/) で学んだUXグロースは、まさに「リリース後にUXを成長させ続ける活動」でした。とくに日常的な高速改善を成立させるには、改善のサイクルを高速に回せる運用の仕組みが欠かせません。

### 仕組みがない場合に起きる問題

「改善し続けたい」という意志だけでは、サイクルは回りません。現場では典型的に2つの壁にぶつかります。

| 壁 | 起きること |
|----|-----------|
| 開発と運用の分断 | リリースが年に数回しかできず、改善案を思いついても世に出せない |
| デザイン業務の属人化 | 画面ごとにデザインがばらつき、毎回ゼロから作るため改善が遅い |

この2つの壁への答えが、それぞれ**DevOps**と**DesignOps**です。

## DevOps（開発と運用の協働）

**DevOps**とは、開発（Development）と運用（Operations）の壁をなくし、**リリースの頻度と品質を同時に高める文化・プラクティス**です。

### 開発と運用が対立する構造

従来、開発チームと運用チームは別々の組織で、目標の向きが逆でした。

- 開発チーム: 新しい機能を早く届けたい（変化を増やしたい）
- 運用チーム: システムを安定して動かしたい（変化を減らしたい）

その結果、リリースは「年に数回の一大イベント」になりがちでした。リリース間隔が長いほど一度の変更が大きくなり、障害のリスクも高まります。

### 代表的なプラクティス

DevOpsは、チームが協働する文化面と、作業を自動化する技術面の両輪で成り立ちます。

| プラクティス | 内容 |
|------------|------|
| CI（継続的インテグレーション） | コードの変更を頻繁に統合し、自動テストで品質を確認する |
| CD（継続的デリバリー） | テストを通った変更を、いつでもリリースできる状態に保つ |
| モニタリング | リリース後の動作やユーザーの反応を常時監視する |
| 開発と運用の一体化 | 「作る人」と「動かす人」を分けず、同じチームで責任を持つ |

### UX改善との関係

DevOpsはエンジニアリング発の言葉ですが、UXにとって重要な土台です。リリースの頻度が高いほど、UX改善の仮説を小さく素早く検証でき、「改善案を出してもリリースは半年後」という停滞がなくなります。

```mermaid

```

## DesignOps（デザイン業務の仕組み化）

**DesignOps**（デザインオプス）とは、デザイン業務を支える仕組みを整備し、**デザイナーがデザインそのものに集中できるようにする運用基盤**です。

### DesignOpsが必要になる背景

サービスやデザイナーの数が増えると、デザイン業務に「仕組みの問題」が生まれます。

- 画面やプロダクトごとにデザインがばらつき、ブランドの一貫性が崩れる
- 同じボタンやフォームを各チームがゼロから作り直す（車輪の再発明）
- ツールや進め方がチームごとに異なり、引き継ぎ・連携のコストが膨らむ
- デザイナーの時間が調整や作り直しに奪われ、本来のデザインに使えない

### 整備する4つの領域

DesignOpsの取り組みは、大きく4つの領域に整理できます。

| 領域 | 内容 | 例 |
|------|------|----|
| デザインシステム | 色・部品・ガイドラインを共通化し、品質と一貫性を担保する | 共通コンポーネント集、UIガイドライン |
| ツールの統一 | デザインツールや管理方法をそろえ、連携コストを下げる | ツール・素材管理の標準化 |
| 採用と育成 | デザイナーの採用・オンボーディング・成長を仕組みで支える | スキル定義、教育プログラム |
| ワークフローの整備 | デザインから開発への受け渡しや確認の流れを標準化する | レビューの定例化、開発との連携ルール |

デザインシステム自体にも運用が必要です。使われない部品を整理し、新しいパターンを取り込み続けて初めて、改善のスピードに貢献します。

## 2つのOpsの共通点

DevOpsとDesignOpsに共通するのは、**個人の頑張りではなく仕組みで継続を支える**という発想です。

| 観点 | DevOps | DesignOps |
|------|--------|-----------|
| 対象 | 開発と運用のプロセス | デザイン業務のプロセス |
| なくす壁 | 開発チームと運用チームの分断 | デザイン業務の属人化・ばらつき |
| ゴール | リリースの頻度と品質を高める | デザイナーがデザインに集中できる |

改善を続ける活動を支える組織づくりと人材育成は、[lesson31](/lessons/lesson31/) で扱います。

## 試験のポイント

- DevOpsは「開発（Development）と運用（Operations）」の合成語。ツールの名前ではなく、**壁をなくす文化・プラクティス**である点を押さえる
- DevOpsの目的は「リリースの頻度**と**品質」の両方を高めること。スピードだけの話ではない
- DesignOpsは「デザイナーがデザインそのものに集中できるようにする運用基盤」。デザイン手法そのものではない
- DevOpsの対象は開発と運用のプロセス、DesignOpsの対象はデザイン業務のプロセス。**対象の違い**で区別する
- 継続的なUX改善は、高速改善（[lesson04](/lessons/lesson04/)）と行動データ分析（[lesson21](/lessons/lesson21/)）を仕組みの面から支える関係にあると整理する
